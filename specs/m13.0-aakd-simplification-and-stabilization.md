# M13.0: Aakd simplification and stabilization

Status: proposed, safe to execute before startup validation
Primary market hypothesis: startups, still unconfirmed
Purpose: simplify the existing Aakd product, remove trust debt, fix defects and make the core contract workflow easy to understand before adding a new wedge.

## Objective

Make Aakd feel like one coherent product:

> Upload a contract, understand what matters, review it safely and keep the important dates and actions visible.

This milestone is product cleanup and workflow improvement. It is not a new CLM architecture and it does not commit Aakd to startups as a permanent ICP.

## In scope

### 1. Truth reset

Remove or correct unsupported claims in all locales:

- SSO/SAML and SCIM
- SOC 2 Type II or readiness
- GDPR tooling claims
- Kubernetes/Helm support unless a maintained chart exists
- free hosted cloud availability
- regulated production customer claims
- invented AI accuracy, usage or adoption metrics

Label features as stable, experimental, planned or unsupported.

### 2. Navigation simplification

Primary navigation should contain only:

- Dashboard
- Contracts
- Obligations and renewals
- Search
- Settings

Move authoring, templates, redlining, signing, analytics, CRM, MCP, imports and AI experiments into secondary or contextual locations. Do not delete their code or data paths in this milestone.

Hide mock or disabled surfaces:

- AI Agents
- Create with AI
- Billing preview
- Hosted-cloud calls to action that cannot be fulfilled

### 3. Core workflow

The first-run path must be:

```text
Create workspace
    |
Upload PDF/DOCX
    |
Extraction and processing state
    |
Review cited fields and confidence
    |
Save contract
    |
See important dates, obligations and next actions
```

The user must not configure an AI provider before uploading a first contract.

### 4. Dashboard emphasis

Keep the current dashboard architecture and existing analytics API. Emphasize the signals users can act on immediately:

- expiring contracts;
- overdue obligations;
- obligations due soon.

Keep approvals and analytics available through their existing screens. Do not add a new action-feed API or redesign the contract page in this milestone.

### 5. Bug and trust fixes

Before changing behavior, run the existing test suite and record the baseline.

Required checks include:

- upload failure and retry states;
- OCR and extraction timeout states;
- missing AI provider state;
- stale extraction job results cannot cross contract or organization boundaries;
- duplicate clicks do not create duplicate obligations;
- navigation during processing does not lose the job state;
- empty states and zero-contract workspaces are useful;
- Arabic RTL and all supported locales render new states;
- organization isolation tests remain green.

### 6. GitHub and setup documentation

- README explains the upload, review and obligation workflow.
- Install documentation states every required service, secret and operational responsibility.
- Documentation distinguishes stable, experimental, planned and unsupported surfaces.
- No seeded demo workspace, installer, CLI, synthetic extraction engine or new demo fixture is introduced in this milestone.

## Out of scope

- New Action Ledger schema
- Agreement-family modeling
- New CRM connectors
- Slack, Teams, Jira, calendar or ERP delivery
- Autonomous agents
- New e-signature functionality
- Enterprise SSO/SCIM
- Billing implementation
- Permanent startup-only product positioning

## Acceptance criteria

- A new user can understand the product and reach upload without configuring AI.
- A user can upload one PDF/DOCX and reach a cited review state with clear progress and failure recovery.
- The default dashboard answers what needs attention next.
- All unsupported public claims are removed or labeled accurately in every locale.
- Mock and disabled features are no longer presented as available product capabilities.
- Existing contract, extraction, obligation, signing, import and organization-isolation tests pass.
- The existing clean-machine setup path is documented truthfully; no install-doctor tooling is added.
- No data model deletion or destructive migration is required.

## Execution slices

1. Baseline tests, route inventory and public-claim audit.
2. Copy and feature-state truth reset.
3. Navigation and onboarding simplification.
4. Dashboard attention-signal emphasis.
5. Extraction and obligation edge-case fixes.
6. README and setup documentation.
7. Full regression, locale and isolation verification.

Each slice should remain small enough to review independently and should not mix product cleanup with speculative new functionality.

## Exit decision

After this milestone, begin startup research and observation. Do not add a new wedge until we know:

- which segment actually uses the core workflow;
- which repeated contract job causes measurable loss or delay;
- who owns the budget;
- whether users return to the workflow;
- whether existing tools already solve it.

The next product investment should be selected from observed startup behavior, not from the current feature list.
