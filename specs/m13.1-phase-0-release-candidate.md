# M13.1: Phase 0 startup-ready release candidate

Status: planned
Owner: engineering
Depends on: `specs/m13.0-aakd-simplification-and-stabilization.md`
Product source of truth: `PRODUCT.md`

## Goal

Make the Phase 0 Aakd core release-ready for startup evaluation without adding
another product surface:

> A startup can upload an executed PDF or DOCX, understand what Aakd extracted,
> correct it safely, save a trustworthy contract record, and assign the next
> contract actions.

This is an engineering release candidate, not proof of product-market fit. The
startup ICP remains a hypothesis until customer evidence changes `PRODUCT.md`.

## Customer job and roadmap mapping

Customer job: turn scattered executed agreements into reviewed facts and owned
deadlines without requiring a legal-ops implementation project.

Roadmap mapping:

- Phase 0: truthful capability boundary, safe activation, cited review,
  obligations, MCP/API security, self-hosting and release evidence.
- Gate A: engineering readiness must pass all automated and disposable-runtime
  checks.
- Gate B: customer evidence remains open and cannot be satisfied by synthetic
  documents, GitHub stars or internal dogfooding.

## Verified facts

- Upload, extraction, cited review, contract storage, obligations, scoped MCP,
  organization isolation and Docker deployment already exist.
- Templates, authoring, autonomous agents, billing and hosted-cloud features are
  paused or hidden from the Phase 0 promise.
- The current source verifier, Compose replay and real Codex MCP replay pass.
- The customer evidence ledger has no verified organizations, paid pilots or
  repeat-use commitments.

## Hypotheses to preserve, not assume

- Startups will prefer a simple upload/review/action workflow over a full CLM
  implementation.
- The first repeated job is post-signature obligation and renewal tracking.
- Local extraction and optional BYOK/Ollama reduce trust and setup friction.
- The current workflow can deliver first value in under ten minutes on a normal
  PDF or DOCX.

## Scope

### 1. Baseline and performance

- Record timings for signup, upload acknowledgement, extraction enqueue,
  extraction completion, contract creation and obligation creation.
- Add visible progress and terminal error states for every asynchronous stage.
- Prevent duplicate submissions and stale polling across navigation, reload and
  expired sessions.
- Keep processing in the worker. No AI, OCR or file parsing runs inline in an
  API route.
- Add focused timing tests around the route and worker boundaries. Do not invent
  a new observability platform.

Release budgets for the local reference corpus:

- upload acknowledgement: under 2 seconds;
- extraction job visible as processing: under 3 seconds after upload;
- first extracted result: under 60 seconds for a 10-page text PDF without an
  external provider;
- contract detail navigation after creation: under 2 seconds at p95 in the
  disposable local stack.

These are engineering budgets, not customer guarantees.

### 2. Contract-first activation

- Make the upload-first route the primary empty-state action.
- Keep AI configuration optional for the first contract.
- Show extracted values with source text, page, confidence and provenance.
- Preserve manual edits as `manual` and never rewrite them as AI output.
- Allow correction before creation and from the saved contract detail page.
- Show a document preview wherever a contract file is available.
- Make extraction failure recoverable with retry, alternate provider guidance and
  a manual metadata path.
- Keep PDF/DOCX validation, size limits and magic-byte checks intact.

### 3. Action workflow

- From the saved contract, expose due dates, renewal/notice information and
  obligations in one clear next-actions section.
- Allow creating, assigning, editing, completing and reopening an obligation.
- Preserve activity/audit records for contract and obligation state changes.
- Make empty, overdue, completed and no-owner states explicit.
- Keep approvals and signing available only where their current flows are
  already stable; do not expand them in this milestone.

### 4. Trust, accessibility and localization

- Replace ambiguous loading states with actionable copy and retry controls.
- Cover all new strings in English, French, German, Spanish and Arabic RTL.
- Check keyboard navigation, focus after dialogs, labels, status announcements
  and contrast for upload, extraction review and obligation forms.
- Never expose organization IDs, storage keys, raw extracted text or unrelated
  member data through UI telemetry or MCP projections.
- Keep document content and credentials out of logs and analytics.

### 5. Release and deployment

- Keep README and environment examples aligned with the actual Compose path.
- Document required services, secrets, worker startup and backup responsibility.
- Run a fresh-volume Compose replay with app, worker, database, Redis, object
  storage and DocuSeal.
- Run the browser suite against the containerized app.
- Run a real Codex MCP replay using a disposable scoped API key.
- Record all results in `research/gates/phase-0-release-evidence-2026-08-17.md`.

## Explicitly out of scope

- Generic agent builder or autonomous legal actions.
- New contract authoring, templates, redlining or editor work.
- New integrations or connectors.
- Billing, hosted Cloud, SSO/SAML/SCIM or compliance certification.
- Agreement-family graph, correction propagation and recipe engine.
- Startup-only pricing or permanent ICP decision.
- Data deletion, destructive migrations or broad refactors.

## Architecture and data flow

```text
Browser
  | authenticated upload / review / action request
  v
API route -- auth + tenant scope + Zod validation + activity attribution
  | store metadata/file, enqueue job
  v
PostgreSQL + S3-compatible storage       Redis/BullMQ worker
  |                                      |
  +----------- cited extraction ----------+
                       |
                       v
              reviewable fact rows
                       |
              human correction / accept
                       v
             contract + obligation state
                       |
             UI, REST and scoped MCP
```

No parallel extraction path, direct storage access, or unscoped agent tool is
allowed in this milestone.

## Verification contract

### Automated checks

- typecheck;
- lint;
- unit and integration tests;
- organization isolation tests;
- API-key and MCP security tests;
- synthetic/adversarial corpus tests;
- production build.

### Browser and runtime checks

- new workspace to first upload;
- PDF and DOCX success paths;
- no-provider extraction fallback;
- manual edit provenance;
- extraction timeout/failure and retry;
- navigation/reload during processing;
- contract preview;
- obligation create, assign, complete and reopen;
- empty, overdue and completed states;
- Arabic RTL smoke path;
- disposable Compose boot and worker health;
- real Codex client `tools/list` plus `list_contracts`.

### Security checks

- viewer cannot mutate through UI, REST or MCP;
- API keys require `text_read` for contract text/Q&A;
- API-key mutations require write scope;
- cross-organization IDs return not-found behavior;
- MCP output remains minimized and tenant-scoped;
- activity records retain actor, source and request attribution;
- no raw contract content or secrets in logs/telemetry.

## Acceptance criteria

The milestone passes only when all are true:

1. A fresh user can reach upload without configuring AI.
2. A valid PDF and DOCX each reach a cited review state or a clear recoverable
   failure state.
3. A manually edited field remains visibly manual after contract creation and
   worker processing.
4. A contract file can be previewed from the relevant contract surfaces.
5. An obligation can be created, assigned, completed and reopened with activity
   evidence.
6. No paused or unsupported feature is presented as available Phase 0 scope.
7. All automated, browser, isolation, Compose and Codex replay checks pass.
8. Release evidence names unresolved customer gates instead of implying them.

## Invalidation conditions

Stop implementation and revisit the plan if:

- a change requires a new data model for the first workflow;
- extraction must run synchronously in an API route;
- the preview requires a new storage or document-rendering service;
- the workflow cannot be tested without an external AI provider;
- the startup ICP is changed from hypothesis to fact without customer evidence;
- a security or tenant-isolation regression appears.

## Execution order

1. Baseline timings and inspect current activation routes/components/tests.
2. Fix loading, failure, retry and manual-provenance behavior.
3. Add/finish preview and contract-detail next-actions presentation.
4. Harden obligation state transitions and empty states.
5. Complete locale, accessibility, telemetry and security regressions.
6. Update deployment and release evidence.
7. Run the complete verification matrix and publish the release-candidate
   decision.

## Next decision after implementation

If Gate A passes, freeze feature work and run customer observation with startup
operators. Require real uploaded corpora, a repeated workflow and paid evidence
before reopening templates, agents, Cloud, pricing or broader CLM expansion.
